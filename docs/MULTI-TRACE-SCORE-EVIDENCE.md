# Canonical raw multi-trace score evidence

`prospect_evidence::multi_trace` persists the exact raw score matrix produced by
`prospect_scenario::multi_trace` without collapsing traces into a statistic or a
winner.

The schema is `prospect.multi-trace-score-evidence/v1`.

## Recorded contract

A `MultiTraceScoreEvidence<Score>` records:

- a run ID;
- sorted, duplicate-free `EvidenceSource` provenance entries;
- an explicit non-empty `metric_id`;
- the semantic ordered scenario-ID contract;
- the semantic ordered trace IDs;
- every raw per-trace/per-scenario score cell.

Trace order and scenario order are preserved because they are part of the matrix
contract. Provenance ordering is normalized because source ordering has no semantic
meaning.

## No implicit aggregation

This schema deliberately contains no mean, median, variance, quantile, confidence
interval, weighting, interpolation, imputation, normalization, aggregate score,
selected candidate, policy winner or Pareto winner.

Any cross-trace reduction requires a separate explicit protocol whose sampling,
weighting and statistical assumptions can be reviewed independently. The raw matrix
must remain available unchanged underneath that later protocol.

## Metric identity

`metric_id` is an application-provided stable label. It is not by itself a software
attestation or version binding. When the exact metric implementation matters, callers
must bind that implementation through `EvidenceSource` revision/content-hash
provenance or another separately trusted contract.

The evidence layer does not infer units, tolerances, quality meaning or scientific
validity from the metric ID.

## Canonical JSON

The constrained-decision and multi-trace evidence modules share one recursive JSON
canonicalizer. Every JSON object key is emitted in lexicographic order, including
nested generic score payloads such as `HashMap` values. Array order is preserved.

`from_canonical_json` uses strict unknown-field rejection, validates the rectangular
trace/scenario contract, reserializes canonically and requires exact byte equality.
Canonical encoding is therefore a consistency property; it is not a digital
signature or trust root.

## Replay

`verify_replay` deliberately ignores run ID and classifies substantive drift into:

- provenance sources;
- metric identity;
- ordered scenario contract;
- trace identities or raw score cells.

No replay comparison is allowed to silently average away a differing trace.

## Evidence boundary

A valid record proves only that the exact structured matrix and provenance fields
satisfy this software contract. It does not prove that the traces are representative,
independent, hardware-observed, generated by a real model, statistically sufficient,
or suitable for latency/throughput/quality claims.

All current validation uses software fixtures. Representative real-model/GPU evidence
remains a separate experimental requirement.
