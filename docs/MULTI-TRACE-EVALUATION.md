# Multi-trace evaluation matrix

`prospect_scenario::multi_trace` groups multiple completed prospective evaluations while preserving each trace as an independent observation.

The goal is to prepare representative campaigns without silently converting several traces into a single statistic. ProspectEngine validates structural comparability; the experimental protocol remains responsible for any later aggregation or statistical inference.

## Trace identity

Each completed `BatchResult` is wrapped in a `TraceBatch` with a non-empty `TraceId`. A `MultiTraceBatch` rejects duplicate trace IDs.

Trace IDs are identifiers only. They do not authenticate a dataset, machine, model, prompt, seed, checkpoint, hardware run or external source. Provenance must be carried by the surrounding evidence layer.

## Structural comparability

Construction is fail-closed. Every trace must expose:

- at least one candidate scenario;
- unique scenario IDs inside that trace;
- the same scenario count as the first trace;
- the exact same ordered scenario IDs;
- the exact same intervention values for corresponding scenarios.

Baselines and resulting signatures may differ by trace. That is the point of the matrix: the same candidate contract can be evaluated under independent states or traces without erasing trace identity.

A reordered scenario list, missing candidate, duplicate scenario ID or intervention drift is rejected rather than aligned heuristically.

## Metric matrix

`MultiTraceBatch::score_matrix` applies an existing `SignatureMetric` independently inside each trace, always comparing that trace's candidates with that trace's own baseline.

The returned `MultiTraceScoreMatrix` preserves:

- exact trace order and `TraceId`;
- exact scenario order and `ScenarioId`;
- every per-trace/per-scenario metric value.

No cross-trace aggregate value is produced.

## Deliberately absent operations

This module does not compute a mean, median, quantile, variance, confidence interval, bootstrap, hypothesis test, weighting, missing-value imputation, interpolation, normalization, policy winner or Pareto winner across traces.

Those operations require an explicit protocol because their validity depends on sampling assumptions, independence, weighting, units, censoring and experiment design. Adding them generically would fabricate scientific semantics that ProspectEngine does not possess.

The canonical constrained-decision evidence layer records decisions over one completed decision set; it does not convert a `MultiTraceScoreMatrix` into a cross-trace winner. Any such bridge must first define an explicit, versioned aggregation/decision protocol rather than reusing single-trace evidence semantics implicitly.

## Intended next layers

A later protocol layer may bind a frozen set of trace identities and define explicit aggregation/statistical rules. A later evidence layer may canonically record the resulting matrix and protocol identity. Neither should alter the raw per-trace values.

For resumed executions, a trace must first be reconstructed as a complete verified `BatchResult` from its parent/child continuation chain before it can enter a `MultiTraceBatch`. Partial or interrupted chains are not valid completed traces.

## Evidence boundary

This is software structure only. It does not prove that traces are representative, independent, observed on hardware, generated by a real model, scientifically valid, or sufficient to establish quality/performance claims.
